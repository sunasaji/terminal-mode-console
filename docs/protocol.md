# even-terminal-compatible HTTP API notes (as of v0.10.4)

Notes on the HTTP API spoken by the Terminal Mode app for the Even Realities G2, covering the range needed for interoperability. terminal-mode-console implements exactly this.

The **sources** are the following two, both of which are entirely self-contained within my own devices:

1. Reading the source of `@evenrealities/even-terminal@0.10.4` (published on npm under the MIT license)
2. Observing the HTTP / SSE traffic between my own app and the server I started myself

The JSON shown below consists of **examples with substituted values** meant to illustrate field structure; it is not the actual traffic content itself. For how this project positions itself, see [`../NOTICE.md`](../NOTICE.md).

> These notes are based on observation of a specific version. They may become outdated as the upstream changes.

## 1. Transport

- Plain Express 5, default port **3456**. Bind address: upstream ≤v0.8.1 used `app.listen(PORT, "0.0.0.0")`; v0.10.x binds a detected private-LAN address plus a loopback listener (with `--tailscale` / `-i` / `--lan` selecting it). terminal-mode-console binds loopback-only by default (`HOST` env to override)
- **No** custom protocol, signing, certificate pinning, or device registration whatsoever
- WebSocket is not used for the display API (the app polls REST + SSE). It backs internal integrations only: the codex app-server (default 8765) and, since v0.10.x, an experimental `claude-sync` transport on the main port. Neither is needed for interop

## 2. Authentication

A single shared token only. Both of the following two routes are accepted:

```http
Authorization: Bearer <token>
?token=<token>
```

### How the app uses each route

**REST and SSE use different routes. A compatible server must support both.**

| Communication           | Authentication method                                                     |
| ----------------------- | ------------------------------------------------------------------------- |
| REST in general         | `Authorization: Bearer <token>` header                                    |
| **SSE (`/api/events`)** | **`?token=<token>` query only. It does not send an Authorization header** |

The reason SSE does not use a header is presumably that Dart's EventSource-family clients cannot set arbitrary headers. **If you implement header authentication only, SSE returns 401 and the screen becomes permanently unresponsive.**

- The default value is `randomBytes(16).toString("hex")`, and **it can be fixed via the `TMCON_TOKEN` environment variable**
- A mismatch returns `401 {"error":{"code":"auth_failed","message":"Unauthorized"}}` on every endpoint (v0.10.x wraps the error in a `{code,message}` envelope; v0.8.1 returned a bare `{"error":"Unauthorized"}` string)
- The token is stored in plaintext in `~/.even-terminal/instances/<pid>.json` (mode 0600)

## 3. CORS

Permissive CORS. Upstream ≤v0.8.1 enabled it unconditionally (`app.use(cors())`); v0.10.x makes it opt-in via `--allow-cors` (off by default). terminal-mode-console always sends `Access-Control-Allow-Origin: *`. OPTIONS response:

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE
```

## 4. Pairing

The contents of the QR code are **just a URL**:

```text
http://<host>:<port>?token=<token>&defaultProvider=<claude|codex>[&name=<EVEN_TERMINAL_NAME>]
```

Generated by `buildClientQuery()`. When using a public tunnel (bore / ngrok / pinggy), only the host portion is replaced.

## 6. SSE (`GET /api/events`)

Headers:

```http
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no
```

- Immediately after connecting, `:ok\n\n`
- The frame format is `id: <n>\ndata: <json>\n\n` (sequential id)
- With `needReplay=true`, the entire ring buffer (**up to 500 entries per session**) is resent
- **Catch-up on reconnect (terminal-mode-console extension)**: when a `Last-Event-ID` header or a
  `?lastEventId=<n>` query is received, only entries **after** that id are resent from the ring buffer
  in order. This lets a reconnection catch up on `text_delta` / `tool_end` that streamed while
  disconnected, as well as `permission_request` / `user_question` awaiting a response.
  - EventSource's automatic reconnect sends `Last-Event-ID` by default (the header route).
  - The WebUI explicitly re-establishes the connection from its side when returning to the foreground. Since a new EventSource
    cannot carry a header, it passes the tracked id via `?lastEventId=` (the query route).
  - After a replay, any currently unanswered `permission_request` / `user_question` is always resent as a state
    snapshot. Pending requests carry a stable `requestId`, and
    the WebUI treats resends of the same request idempotently, so it preserves the card or an in-progress answer.
- Every **15 seconds**, `:heartbeat\n\n`

The heartbeat is solely for keeping the connection alive and does not update the agent activity timestamps below. An EventSource disconnect is shown as
the WebUI's `Reconnecting...`, distinct from a state where the agent is not emitting events.

### Foreground turn liveness (terminal-mode-console extension)

`startedAt` is the start of the current foreground turn, `lastActivityAt` is the epoch milliseconds at which the last
meaningful agent event was observed, and `activityKind` is that event's kind. Activity means
`think_start/end`, `text_start/delta/end`, `tool_start/end`, and `result`. SSE heartbeats, connections,
notifications (including the silence warning itself), display timers, and waiting for a user answer do not count as activity.

The values do not assert stoppage or the usefulness of the work. Even normal long-running processing that emits no events can result in
`No activity`. The notification when `STALL_WARN_MS` is reached fires only once per contiguous inactivity interval, and
the turn is not auto-interrupted and the process is not auto-restarted. No warning is issued during `status:waiting`, and
the `status:background` that arrives after the foreground ends, together with its subsequent events, is not mixed into foreground liveness.

### Event types

All kinds that could be observed. Values are examples:

```jsonc
{"type":"user_prompt","text":"..."}
{"type":"status","state":"busy|idle|think_start|think_end|text_start|text_end","sessionId":"..."}
{"type":"text_delta","text":"partial "}                 // high frequency, a few characters at a time
{"type":"tool_start","name":"Read","toolId":"<toolUseId>"}
{"type":"tool_end","name":"WebSearch","toolId":"<toolUseId>","summary":"Search \"...\"","detail":{"input":{},"output":""}}
{"type":"running_stats","durationMs":140013,"inputTokens":26384,"outputTokens":813}  // every 10 seconds
{"type":"result","success":true,"text":"...","sessionId":"...","costUsd":0.0142,"provider":"claude","turns":1,"durationMs":14936,"inputTokens":0,"outputTokens":0,"model":"claude-opus-4-6"}  // model is an extension: the concrete model ID actually used for this turn (Claude / Codex; null when unavailable)
{"type":"user_question","questions":[{"question":"...","header":"...","options":[{"label":"","description":"","preview":""}]}],"toolUseId":"..."}
{"type":"question_answer","answers":{"<question>":"<label>"}}
{"type":"permission_request","toolName":"Bash","description":"...","detail":"...","toolUseId":"...","options":[{"text":"Yes","key":"allow"}],"suggestions":null}
{"type":"permission_result","toolName":"...","summary":"...","decision":"allowed|always|denied"}
{"type":"task_progress","completed":3,"total":5,"current":"..."}
{"type":"notification","title":"...","message":"..."}
{"type":"error","message":"..."}
```

After notifying a retryable problem via `error`, the Codex App Server reports the final result of the turn through
the `status` in `turn/completed`. terminal-mode-console holds onto intermediate `error`s temporarily and
converts them into the `error` event above only when the final result is `failed`. This way, even when an assistant response fails
with an empty body due to a usage limit or similar, it displays the reason before returning to `status:idle`.
When a retry succeeds, the intermediate error is not shown.

terminal-mode-console extensions (not present officially; the app ignores unknown fields / unknown states):

```jsonc
{"type":"status","state":"waiting","waitingFor":"permission|question","label":"Allow Bash","sessionId":"..."}
{"type":"status","state":"background","count":1,"sessionId":"..."}   // a background agent is running
{"type":"permission_result","decision":"denied","cancelled":true}   // the wait was released by an interrupt
{"type":"question_answer","answers":{...},"cancelled":true}
```

#### Visualizing background agents (claude backend)

The Agent (sub-agent) tool in Claude Code 2.1.2xx runs in the background by default.
The foreground turn launches the sub-agent and immediately returns `result` (the `bus` emits `idle`), and completion
arrives later as subsequent events triggered by a task-notification. At this point, if the bottom line stays at `Waiting input`,
"running / completed / stopped" cannot be distinguished, so the following are emitted:

- Start of execution (0→1 entries): `notification` "⏳ Running in background" + the extension `status:background`
- Sub-turn completion (others still running): `notification` "Background update" (with progress in the body)
- All complete (→0 entries): `notification` "✅ Background complete" + `status:idle`
- Interrupt: `notification` "⏹ Background stopped" + `status:idle`

The stock glasses app ignores the unknown `status:background`, so the persistent dim
`notification` line becomes the main means of distinction. The WebUI displays `status:background` on the bottom line
as "Running in background".

When the foreground turn becomes empty, `bus` does not unconditionally emit `idle`; instead it queries the adapter's
`backgroundStatus(session)`, and if a background job is running, it emits that `status:background` in place of `idle`.
This prevents the WebUI from momentarily returning to `Waiting input` after a foreground turn ends,
and while running it keeps showing "Running in background" (when everything completes, the adapter emits
`idle` and returns to `Waiting input`).

### Event order within one turn

```text
user_prompt → status:busy
  → [status:think_start → status:think_end]        # when extended thinking runs
  → [tool_start → tool_end]*                       # once per tool use
  → status:text_start → text_delta* → status:text_end
  → result → status:idle
```

`running_stats` interrupts at 10-second intervals during busy.

## 7. Timeouts

Values in the official implementation:

- Waiting for a permission response: **60 seconds** (deny if no response)
- Waiting for a question response: **120 seconds** ("skip" if no response)
- SSE heartbeat: 15 seconds

**terminal-mode-console intentionally does not adopt these two response-wait timeouts.** If an answer is
auto-finalized on no response, the answer gets decided on its own while the user is still thinking, and the conversation
just proceeds (in practice, a three-way AskUserQuestion choice was treated as "skip" at exactly 120 seconds, and
the model continued with its own recommended option). terminal-mode-console **waits indefinitely until the user responds or an explicit interrupt
(`POST /api/interrupt`)**. The SSE heartbeat stays at 15 seconds.

Since it waits indefinitely, the fact that it is waiting must be visible, so the following are added:

- When it enters a wait, it emits `status:waiting` (extension) and a `notification`.
  Because the glasses ignore unknown `status`, the `notification`, which becomes a single dim line, serves as a fallback.
- **To clients that re-establish SSE while still awaiting a response, the pending request is resent**
  (this prevents a situation where no one can answer after a WebUI reload, an app restart, or a phone returning to the foreground).
  It is resent as the current state regardless of whether an incremental/full replay occurred, and the WebUI identifies
  the same request by `requestId` to prevent duplicate display or the loss of an in-progress answer.
- The `permission_result` / `question_answer` emitted when an interrupt clears the wait carries
  `cancelled: true` (extension), so that the case where no one answered can be distinguished.

## 7.5 App-side behavior

The client is built with Flutter / Dart (`User-Agent: Dart/3.11 (dart:io)`), `accept-encoding: gzip`.

### Session list

It polls `GET /api/sessions?provider=claude` **at 10-second intervals**.

### Creating a new session

**No API communication occurs at all.** It is merely local state inside the app; the session on the server
is created by the first prompt. **A "session creation API" is unnecessary.**

### Sending a prompt (new session)

**It sends unused fields explicitly as `null` rather than omitting them**:

```json
{ "text": "hello", "sessionId": null, "cwd": null, "provider": "claude" }
```

Since `cwd: null`, **the cwd of a new session is determined by the server's `PROJECT_DIR` (the cwd at startup)**.
Write a compatible server on the assumption that `sessionId` / `cwd` may arrive as `null`
(a check equivalent to `if (sessionId)` is null-safe).

### Sending a prompt (existing session)

**Unlike a new session, `cwd` contains a real value** (the cwd returned by the list API comes back as-is):

```json
{
  "text": "…",
  "sessionId": "<sessionId>",
  "cwd": "/path/to/project",
  "provider": "claude"
}
```

In other words, `cwd` is null only for a new session. A compatible server must handle
**both null (= use the default cwd) and a real value (= use it)**.

### Prompt with images (extension, optional)

The glasses app does not send these, but they are extension fields for self-made clients such as the WebUI.
If you put **an array of data-URL or raw base64 strings** in `images`, a Vision-capable backend inserts the images into the
user message. `text` may be omitted (images only are allowed).
Both the `local` (OpenAI Vision-style `image_url`) and `claude` (Anthropic image blocks) backends support this. `claude`
switches the prompt to the streaming-input form and places it in the content array only when there are images
(without images, it is a string prompt as before).

```json
{
  "text": "describe this image",
  "images": ["data:image/png;base64,iVBORw0..."],
  "sessionId": null,
  "provider": "codex"
}
```

The total size is limited by `MAX_PROMPT_IMAGE_CHARS` (the sum of base64 characters). Exceeding it is **413**.
If `images` is not a string array, it is **400**. When you want to have an image file analyzed in the conversation's context,
there is also a route where you have the model call the `view_image` tool (see README "Tool use with local LLMs").

### Session usage (WebUI extension, optional)

`GET /api/usage?sessionId=<id>&provider=<claude|codex>` returns the current context usage rate and plan-quota usage rate
shown in the WebUI's status line. The WebUI fetches it when it connects to a session and on `status:idle`
(turn completion).

```json
{
  "available": true,
  "context": { "utilization": 50 },
  "fiveHour": { "utilization": 40, "resetsAt": "2026-09-13T10:00:00Z" },
  "sevenDay": { "utilization": 30, "resetsAt": "2026-09-20T10:00:00Z" }
}
```

`utilization` is a percentage from 0 to 100, and `resetsAt` is ISO 8601. The WebUI converts `resetsAt` to
the browser's local time and displays it as `YYYY/MM/DD(day) HH:MM` (without seconds). When an individual value cannot be obtained,
that item can be set to `null`. When the backend does not support usage retrieval, or when it cannot be obtained due to the connection type,
it returns `{"available":false}` and the WebUI does not show the usage field.
For Claude, the source is the Agent SDK's structured context/usage; for Codex, it is the latest `token_count` saved in the rollout.
This is not an API used by the stock glasses app; it is a
compatible-server-specific extension.

### Permission request round-trip

Server → app (SSE):

```json
{
  "type": "permission_request",
  "toolName": "Bash",
  "description": "Bash Create a directory",
  "detail": "mkdir -p /tmp/example",
  "toolUseId": "<toolUseId>",
  "options": [
    { "text": "Yes", "key": "allow" },
    {
      "text": "Yes, and always allow Bash rule `mkdir -p /tmp/example` in local settings",
      "key": "allowAlways"
    },
    { "text": "No", "key": "deny" }
  ],
  "suggestions": [
    {
      "type": "addRules",
      "rules": [{ "toolName": "Bash", "ruleContent": "mkdir -p /tmp/example" }],
      "behavior": "allow",
      "destination": "localSettings"
    },
    {
      "type": "addDirectories",
      "directories": ["/tmp"],
      "destination": "session"
    }
  ]
}
```

App → server (REST):

```json
POST /api/permission-response
{"sessionId":"<sessionId>","decision":"allow","provider":"claude"}   → 200 {"ok":true}
```

- **`decision` is the `options[].key` returned as-is** (`allow` / `allowAlways` / `deny`).
  The app displays `text` and sends `key`. A compatible server can define options freely.
- From reading it on the glasses to selecting, it was a little over 10 seconds in practice. This fits within the official 60-second timeout, but
  if you hesitate it will of course exceed it (see §7 for why terminal-mode-console keeps waiting).
- Immediately afterward, `permission_result` streams (`decision` is **converted** to
  `allowed` / `always` / `denied` — note that the vocabulary and spelling differ from the request side).

### Question response round-trip

Server → app (SSE). **Multiple questions can be sent at once**:

```json
{
  "type": "user_question",
  "toolUseId": "<toolUseId>",
  "questions": [
    {
      "question": "Which colour do you prefer?",
      "header": "Colour",
      "options": [
        { "label": "Red", "description": "prefers red", "preview": "" },
        { "label": "Blue", "description": "prefers blue", "preview": "" }
      ]
    },
    {
      "question": "Which season do you prefer?",
      "header": "Season",
      "options": [
        { "label": "Summer", "description": "prefers summer", "preview": "" },
        { "label": "Winter", "description": "prefers winter", "preview": "" }
      ]
    }
  ]
}
```

App → server (REST). **`answer` is double-encoded, i.e. JSON stringified**:

```json
POST /api/question-response
{"sessionId":"<sessionId>",
 "answer":"{\"Which colour do you prefer?\":\"Red\",\"Which season do you prefer?\":\"Winter\"}",
 "provider":"claude"}
  → 200 {"ok":true}
```

**Most important**: `answer` is **a string, not an object**. Its contents are JSON of
`{question text: chosen label}`. The server does `JSON.parse(answer)`, and
has a fallback that, on failure, treats it as "the same string for all questions".

- The key is not `header` but **the full text of `question`**.
- The value is `options[].label` as-is (not `description`).
- Implement it so it branches on the success/failure of `JSON.parse` (a route where a plain string arrives still exists).

After finalizing, the server streams `question_answer` to SSE (this one is **an already-parsed object**):

```json
{
  "type": "question_answer",
  "answers": {
    "Which colour do you prefer?": "Red",
    "Which season do you prefer?": "Winter"
  }
}
```

Selecting two questions took 13 seconds in practice. The official timeout is 120 seconds (terminal-mode-console is indefinite — §7).

### Communication order within one turn

```text
T+0ms      POST /api/prompt              → 202 {ok, sessionId, provider}
T+325ms    GET  /api/events?token=…&sessionId=<ID from the 202>   ← the SSE is opened afterwards
T+1.8s     SSE  status:text_start
T+1.8s     SSE  text_delta …
T+2.0s     SSE  status:text_end
T+2.1s     SSE  result
T+2.6s     SSE  status:idle
```

Important implications:

- **SSE is established after the POST**. It connects using the `sessionId` returned in the 202.
- Because of this, **`user_prompt` and `status:busy` are missed** (they already fired before the connection).
  The app does not care about this = a compatible server may likewise assume they are missed.

### Opening an existing session

```text
T+0ms      GET /api/events?token=…&sessionId=<sessionId>                  ← the SSE comes first
T+165ms    GET /api/sessions/<sessionId>/history?limit=10&provider=claude
```

**The order is SSE → history**. `limit` is always 10.

### `needReplay` is not used

In both the new and existing cases, **the app does not send `needReplay`**.
The query is always just the two `?token=<token>&sessionId=<id>`.
The server-side replay mechanism is effectively never used by the app.
**A compatible server works even without implementing replay.**

### Turns can be started from outside the app too (verified on hardware)

`POST /api/prompt` is not an app-exclusive endpoint. With just the token, any client
(curl, a web page, a CLI) can submit a prompt to the same session, and **exactly the same sequence of events as a turn sent by the app**
streams. The server does not distinguish the sender.

```text
POST /api/prompt (from curl) → 202
  status: busy → status: text_start
  text_delta … → status: text_end
  result → status: idle
```

On the glasses too, **both the injected prompt text and the response body are rendered as usual**.

Implication: you are not bound to the app's input method (voice). Sending a long text from a device with a keyboard and
reading the result on the glasses **works without changing the existing server**.

### Multiple clients can connect to one session simultaneously (verified on hardware)

While the app has SSE established, if another client connects to `/api/events` with the same `sessionId`,
**both receive the same events**. There is no contention.

This is enough for multiplexing output. On the other hand, **input is not mutually excluded**, so
handling a second `POST /api/prompt` that arrives during turn execution is the implementation's responsibility
(if you write a compatible server, provide queuing or a 409).

### The SSE connection does not close when a session is closed

- Closing a session on screen does not cause a disconnect.
  **Re-opening the same session runs neither a new connection nor a history fetch** (the connection is reused).
- Switching to a different session **adds a new connection**. The old connection stays open.
  Connections accumulate each time a session is opened.
- Therefore a compatible server must:
  - **Assume long-lived connections**. Do not cut them with an idle timeout.
  - The 15-second heartbeat is essential to avoid being cut by NAT / intermediate devices.
  - **Multiple clients may coexist on one session** (broadcast to all of them).
  - When cut from the server side, **the app does not auto-reconnect**.
    Since a restart of the app becomes necessary, avoid restarting the server as much as possible.

## 7.6 Rendering on the glasses

Results of actually sending each event and checking the G2 display.

| Event           | How it appears                                                                                                                                                                                                   |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `notification`  | One line appended in **dim text**. In the form `> <title> <message>`, with **title and message concatenated on the same line**. It does not auto-dismiss and stays                                               |
| `error`         | One line appended at **normal brightness**. Existing lines scroll up. There is **no** special treatment as an error case (color, emphasis, state change). The bottom line's "Waiting input" also does not change |
| `task_progress` | **Never appears on screen at all**. No change while idle, nor even in a state where `status:busy` was sent                                                                                                       |

The difference between `notification` and `error` is **brightness only**, which is weak as a means of conveying severity.
Information you want to convey reliably is better mixed into the `text_delta` body.

### Screen during turn execution

The bottom line (status line):

- When idle: `Waiting input`
- While running: it changes to a gerund display like `Planning...` / `XXXing...`, and
  **the elapsed time since the turn started (seconds → minutes+seconds) counts up every second**.

Each time a tool runs, one line is appended to the body in **dim text** (the same dim display as `notification`):

```text
> tool end: TodoWrite・TodoWrite update tasks
> tool end: Bash / ran "Bash sleep 20"
```

The format is `> tool end: <name>・<summary>`. The `name` and `summary` of the `tool_end` event
are used as-is (`detail` is not displayed).

### The status line is driven by `status` events. However, not all states are visible

The status line (bottom line) switches on the SSE `status`. It was confirmed on hardware that **it switches even for a turn the app did not send
—— a turn injected from outside via `POST /api/prompt`**.

| `state`                     | Bottom line                                                        |
| --------------------------- | ------------------------------------------------------------------ |
| `think_start` → `think_end` | Shows **`Thinking...`**                                            |
| `busy`                      | **No visible label**. Sent on its own, it stays at `Waiting input` |
| `idle`                      | Returns to `Waiting input`                                         |

The fact that `busy` has no visual change is confusing. It fits the actual behavior to think of `busy` as an internal state,
with `think_start` / `text_start` being the ones that carry a display.

Meanwhile, **the elapsed-seconds counter is the app's local timer**. Since `running_stats` comes only at
10-second intervals, the per-second count-up cannot be explained by SSE.

**Implication for a compatible server**: if you send `status: think_start`, you can show
"Thinking..." for the server's own reasons. It becomes a practical means to keep the glasses from looking unresponsive
during a local LLM's inference or during time-consuming preprocessing. Send `think_end` when done.

### `task_progress` does not actually fire

Even streaming a longer turn that repeatedly calls TodoWrite yielded **0 entries**. Following the source shows
this event is effectively unreachable:

- The only place it is sent is the `if (toolName === "TodoWrite")` block inside `canUseTool`.
- However, **TodoWrite does not go through `canUseTool`** (it is auto-approved on the SDK side).
  Within what was observed, the only calls to `canUseTool` were for **Bash and AskUserQuestion**.
- As a result, even though TodoWrite itself is used many times, not a single
  SSE broadcast of `task_progress` occurs.

Therefore it is only natural that nothing appears in the app, and whether or not the app implements it
cannot be determined from the server. **If you want to show progress on a compatible server, write it out in `text_delta`
like `[2/5] …`.**

As a confusingly different thing, the `{"type":"system","subtype":"task_progress",…}` that appears in the log is
**the Agent SDK's sub-agent progress** and is unrelated to even-terminal's SSE events.
Since `processSystem()` handles only `api_retry`, this one is discarded.
A compatible server has room to pick this up and visualize sub-agent progress.

## 8. Unconfirmed matters

- **The strictness of the app's input validation.** The above is a contract derived from the server's implementation and actual responses, and
  it does not cover how the app reacts to unknown or missing fields.
- Version differences. What is written here is observation as of v0.10.4, and it may change with upstream updates. Notable changes since v0.8.1: the structured `{code,message}` error envelope for 401 and `/info` failures, the `extra.expose` field on `/info`, stricter `/permission-response` validation (404/400), a new experimental `claude-sync` provider name (accepted alongside `claude`/`codex`; it wraps the real `claude` CLI over a WebSocket + loopback hook endpoint, an internal mechanism terminal-mode-console does not reimplement), CORS now opt-in (`--allow-cors`), and binding to a private LAN address instead of `0.0.0.0`.
  Verifying in your own environment is the sure way.

## 9. Security notes

Even when building your own compatible server, the following properties are shared with the official implementation:

- Because it listens on a LAN address + a single token, **it is reachable from other devices on the same LAN** (upstream ≤v0.8.1 bound `0.0.0.0`; v0.10.x binds a private-LAN address; terminal-mode-console defaults to loopback-only)
- When CORS is enabled (unconditional up to v0.8.1, opt-in via `--allow-cors` in v0.10.x, always on in terminal-mode-console), it can be hit with `?token=` from any page opened in a browser
- `POST /api/prompt` can submit an arbitrary prompt to a session = effectively an RCE route

Keep up operational practices such as limiting it to a private network like Tailscale and keeping the token unguessable.
